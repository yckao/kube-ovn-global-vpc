# Quick start: two sites with two gateways each

> Legacy experimental API reference. New deployments should start with the
> [managed VPC quick start](managed-quickstart.md).

This guide deploys the legacy **D implementation**, `site-vpc-controller`, into
two existing Kube-OVN Infra clusters. It connects one routed tenant VPC using
WireGuard/BGP, with two gateways on distinct nodes in each site. Each controller
uses only its local Kubernetes API and OVN databases.

The examples are in [`config/examples/site-autonomous`](../config/examples/site-autonomous).
They include the paired peer lists; you do not need to derive Site B from Site A.
Do **not** apply that directory recursively: the two site registrations have the
same ConfigMap name and belong in different clusters.

This is an alpha deployment example, not a production HA installer. It has
static gateway registration and one active controller per local attachment.
There is no Gateway Directory, route reflector, automatic gateway-node
replacement, or rolling membership/key/transport change yet. Gateway Pods and
their runtime ConfigMaps are generated by the controller.

## 1. Check prerequisites and build the images

You need:

- Two existing local Infra clusters with working Kube-OVN networking. The
  multi-gateway API requires the native BFD-only Vpc port and ECMP support
  supplied by Kube-OVN v1.16.4; verify the target installation capabilities.
- Two available Linux gateway nodes per cluster, with WireGuard support and
  existing bidirectional underlay IP/UDP connectivity. The example uses UDP
  51820 and 51821 on each node. Reserve these ports and all address pools first.
- At least two eligible local OVN HA chassis for the native BFD-only Vpc port.
  Registering two gateway nodes does not itself configure these chassis. See the
  [local OVN ownership and availability requirements](multi-gateway-ha.md#explicit-local-ownership).
- Existing local `kube-system/deployment/ovn-central`, container `ovn-central`,
  exposing `/run/ovn/ovnnb_db.sock` and `/run/ovn/ovnsb_db.sock`. Adjust the
  registration commands if your installation differs.
- Administrative `kubectl` contexts for both clusters, a Docker/BuildKit builder,
  a registry reachable from their nodes, Python 3, and the `wg` command locally.

Run from the repository root. Replace the registry and choose the gateway nodes'
architecture (`linux/amd64` is an example). These image names are placeholders;
this repository does not publish ready-made controller images.

```sh
export CTX_A=replace-with-site-a-context
export CTX_B=replace-with-site-b-context
export CONTROLLER_IMAGE=registry.example.com/global-vpc/site-vpc-controller:quickstart-1
export GATEWAY_IMAGE=registry.example.com/global-vpc/site-gateway:quickstart-1

docker build --platform linux/amd64 \
  -f build/site-controller.Dockerfile \
  -t "$CONTROLLER_IMAGE" .
docker build --platform linux/amd64 -t "$GATEWAY_IMAGE" gateway/
docker push "$CONTROLLER_IMAGE"
docker push "$GATEWAY_IMAGE"
```

The controller image includes Python, kubectl, the adapter, and all three gateway
runtime modules. OVN commands run inside the local OVN central container. Set
`--build-arg KUBECTL_VERSION=vX.Y.Z` on the controller build when needed for the
target API version. Pin your tested images by digest for a durable deployment;
do not overwrite a tag after a SiteVpc has accepted its registration.

For a private registry, provision pull credentials for the controller ServiceAccount
and the gateway namespace's **default** ServiceAccount, or configure node-level
registry access. Generated gateway Pods currently use the default ServiceAccount
and do not have an explicit `imagePullSecrets` field.

## 2. Install the local API and permissions in both clusters

```sh
mkdir -p .private/quickstart
cp config/examples/site-autonomous/*.yaml .private/quickstart/

for ctx in "$CTX_A" "$CTX_B"; do
  kubectl --context "$ctx" apply -f config/crd/networking.globalvpc.io_sitevpcs.yaml
  kubectl --context "$ctx" wait --for=condition=Established \
    crd/sitevpcs.networking.globalvpc.io --timeout=60s
  kubectl --context "$ctx" apply -f .private/quickstart/namespace.yaml
  kubectl --context "$ctx" apply -f config/rbac/site.yaml
  kubectl --context "$ctx" apply -f .private/quickstart/ovn-exec-rbac.yaml
done
```

The namespace allows privileged, host-PID gateway Pods; restrict access to
platform administrators. This example's OVN access Role grants **Pod exec in
kube-system**. RBAC does not restrict the command being executed. Direct OVN TLS
access is an alternative requiring separately provisioned credentials and OVN
client binaries. The controller itself runs without privilege.

The local kubeconfig ConfigMap refers to the controller Pod's rotating
ServiceAccount token and local API CA. It contains no token and no remote API
credentials. Do not create a long-lived administrator kubeconfig Secret for this
same-cluster example.

## 3. Fill in the two registrations and create local key Secrets

The example allocation is:

| Setting | Site A | Site B |
| --- | --- | --- |
| Site / attachment | `site-a` / `infra-a` | `site-b` / `infra-b` |
| Global VPC identity | `tenant-red` | `tenant-red` |
| Delegated workload pool | `10.241.0.0/16` | `10.242.0.0/16` |
| Local workload subnet | `10.241.0.0/24` | `10.242.0.0/24` |
| Local transit subnet | `10.240.255.0/29` | `10.240.254.0/29` |
| Gateway transit addresses | `10.240.255.2`, `.3` | `10.240.254.2`, `.3` |
| Local OVN BFD source | `10.254.120.1` | `10.254.120.2` |
| Gateway underlay addresses | `198.51.100.10`, `.11` | `198.51.100.20`, `.21` |
| Local gateway ASN | `64512` | `64513` |

The underlay addresses are documentation addresses: replace them with existing
reachable node addresses. These gateway ASNs do not change host or ToR BGP.
Control-link addresses `10.254.110.1` through `.8` must also be reserved. Adapt
the sample workload/transit/BFD pools if they conflict with your environment.
Workload pools in the **same** VPC must not overlap across sites.

Populate the real cluster and namespace UIDs, and the built image references:

```sh
python3 - <<'PY'
import os
import subprocess
from pathlib import Path

directory = Path('.private/quickstart')
for site in ('a', 'b'):
    context = os.environ['CTX_' + site.upper()]
    path = directory / f'site-{site}-config.yaml'
    text = path.read_text()
    for namespace, placeholder in (
        ('kube-system', f'REPLACE-WITH-SITE-{site.upper()}-KUBE-SYSTEM-UID'),
        ('global-vpc-system', f'REPLACE-WITH-SITE-{site.upper()}-GATEWAY-NAMESPACE-UID'),
    ):
        uid = subprocess.check_output(
            ['kubectl', '--context', context, 'get', 'namespace', namespace,
             '-o', 'jsonpath={.metadata.uid}'], text=True).strip()
        if not uid:
            raise SystemExit(f'Missing namespace UID: {context}/{namespace}')
        text = text.replace(placeholder, uid)
    text = text.replace('registry.example.com/global-vpc/site-gateway:dev',
                        os.environ['GATEWAY_IMAGE'])
    path.write_text(text)
path = directory / 'deployment.yaml'
path.write_text(path.read_text().replace(
    'registry.example.com/global-vpc/site-vpc-controller:dev',
    os.environ['CONTROLLER_IMAGE']))
PY
```

Create four different WireGuard keys. Run this once for a fresh installation;
do not rerun to rotate an accepted registration. Private keys stay in ignored
local files and their own site's Secrets. The commands below do not print them.

```sh
(
  set -eu
  umask 077
  for site in a b; do
    for member in 1 2; do
      key=".private/quickstart/site-${site}-gw-${member}.key"
      test ! -e "$key"
      wg genkey > "$key"
      wg pubkey < "$key" > "${key}.pub"
    done
  done
)

for member in 1 2; do
  kubectl --context "$CTX_A" -n global-vpc-system create secret generic \
    "tenant-red-wireguard-${member}" \
    --from-file="privateKey=.private/quickstart/site-a-gw-${member}.key"
  kubectl --context "$CTX_B" -n global-vpc-system create secret generic \
    "tenant-red-wireguard-${member}" \
    --from-file="privateKey=.private/quickstart/site-b-gw-${member}.key"
done

python3 - <<'PY'
from pathlib import Path
directory = Path('.private/quickstart')
for site, remote in (('a', 'b'), ('b', 'a')):
    path = directory / f'site-{site}-config.yaml'
    text = path.read_text()
    for member in (1, 2):
        public = (directory / f'site-{remote}-gw-{member}.key.pub').read_text().strip()
        text = text.replace(
            f'REPLACE-WITH-SITE-{remote.upper()}-GATEWAY-{member}-PUBLIC-KEY', public)
    path.write_text(text)
PY
```

Now edit these two files:

- `.private/quickstart/site-a-config.yaml`: set two actual Site A `nodeName`
  values and replace Site B's `198.51.100.20` / `.21` endpoints.
- `.private/quickstart/site-b-config.yaml`: set two actual Site B `nodeName`
  values and replace Site A's `198.51.100.10` / `.11` endpoints.

Both ends of each link already have reversed control addresses and matching
UDP ports. Preserve that pairing. The same `gatewayRevision` / `revision` is
already set in both local files. If needed, adapt the OVN namespace, deployment,
container and socket paths, together with `ovn-exec-rbac.yaml`, before accepting
any SiteVpc. Reapply that RBAC file if changed.

Check that no placeholders or documentation endpoints remain before continuing:

```sh
rg -n 'REPLACE-WITH|replace-with|registry\.example\.com|198\.51\.100\.' \
  .private/quickstart/site-*-config.yaml .private/quickstart/deployment.yaml
```

Expected: no output (ripgrep exits 1 when there are no matches).

## 4. Deploy the local controllers, then create the VPC attachments

```sh
kubectl --context "$CTX_A" apply -f .private/quickstart/site-a-config.yaml
kubectl --context "$CTX_B" apply -f .private/quickstart/site-b-config.yaml

for ctx in "$CTX_A" "$CTX_B"; do
  kubectl --context "$ctx" apply -f .private/quickstart/deployment.yaml
  kubectl --context "$ctx" -n global-vpc-system rollout status \
    deployment/site-vpc-controller --timeout=180s
done

kubectl --context "$CTX_A" apply -f .private/quickstart/site-a-vpc.yaml
kubectl --context "$CTX_B" apply -f .private/quickstart/site-b-vpc.yaml
```

`SiteVpc` is **cluster-scoped**, so its YAML has no namespace. Both clusters use
the same `globalVpcID`, but each object has its own local subnet and Kubernetes
UID. The controller creates the local Kube-OVN Vpc, workload/transit Subnets,
two gateway Pods and their runtime ConfigMaps, and local BFD/ECMP configuration.
It does not create tenant workloads.

Keep controller `replicas: 1` and `strategy: Recreate`. The current Lease does not
fence a stale process's external commands. Confirm an old controller has stopped
before replacement; do not force-delete an unreachable controller Pod and assume
the Lease prevents two writers. The two **gateways** are active-active.

## 5. Verify local readiness and cross-site forwarding

```sh
for ctx in "$CTX_A" "$CTX_B"; do
  kubectl --context "$ctx" wait --for=condition=LocalReady \
    sitevpc/tenant-red-local --timeout=180s
  kubectl --context "$ctx" wait --for=condition=GatewayRedundant \
    sitevpc/tenant-red-local --timeout=180s
  kubectl --context "$ctx" get sitevpc tenant-red-local -o yaml
  kubectl --context "$ctx" -n global-vpc-system get pods \
    -l networking.globalvpc.io/gateway=true -o wide
  kubectl --context "$ctx" -n global-vpc-system logs \
    deployment/site-vpc-controller --tail=50
done
```

Expected per site: one controller, two gateway Pods on different nodes,
`LocalReady=True` and `GatewayRedundant=True`. Deployment probes only check the
controller process; SiteVpc conditions check local convergence. Neither proves
cross-site connectivity.

If status reports `waiting for native BFD port with at least two chassis`, check
the local Kube-OVN BFD port support and its eligible HA chassis; adding controller
replicas will not resolve it.

Inspect BGP and BFD on **both** gateways in each site:

```sh
for ctx in "$CTX_A" "$CTX_B"; do
  for pod in $(kubectl --context "$ctx" -n global-vpc-system get pods \
    -l networking.globalvpc.io/gateway=true -o name); do
    kubectl --context "$ctx" -n global-vpc-system exec "$pod" -- \
      vtysh -c 'show bgp ipv4 unicast summary'
    kubectl --context "$ctx" -n global-vpc-system exec "$pod" -- \
      vtysh -c 'show bfd peers'
    kubectl --context "$ctx" -n global-vpc-system exec "$pod" -- \
      ip -4 route show
  done
done
```

Expect two remote eBGP peers plus one same-site sibling iBGP peer per gateway.
The opposite workload `/24` should be learned and installed. If local readiness
succeeds but remote BGP does not, check endpoint addresses/ports, public-key
pairing and actual underlay reachability.

Create a small HTTP test Pod on each generated workload Subnet. This script
reads the Subnet name from `SiteVpc.status.resources` and renders the local
annotation; it never selects the protected transit Subnet (`st-*`).

```sh
python3 - <<'PY'
import os
import subprocess
import json
from pathlib import Path

directory = Path('.private/quickstart')
for site in ('a', 'b'):
    context = os.environ['CTX_' + site.upper()]
    obj = json.loads(subprocess.check_output(
        ['kubectl', '--context', context, 'get', 'sitevpc',
         'tenant-red-local', '-o', 'json'], text=True))
    names = [r['name'] for r in obj['status']['resources']
             if r['kind'] == 'Subnet' and r['name'].startswith('ss-')]
    if len(names) != 1:
        raise SystemExit(f'Expected one ready workload Subnet in {context}')
    text = (directory / 'smoke-pod.yaml').read_text().replace(
        'REPLACE-WITH-LOCAL-WORKLOAD-SUBNET', names[0])
    (directory / f'site-{site}-smoke.yaml').write_text(text)
PY

kubectl --context "$CTX_A" apply -f .private/quickstart/site-a-smoke.yaml
kubectl --context "$CTX_B" apply -f .private/quickstart/site-b-smoke.yaml
for ctx in "$CTX_A" "$CTX_B"; do
  kubectl --context "$ctx" -n global-vpc-smoke wait --for=condition=Ready \
    pod/tenant-red-smoke --timeout=120s
done

POD_IP_A=$(kubectl --context "$CTX_A" -n global-vpc-smoke \
  get pod tenant-red-smoke -o jsonpath='{.status.podIP}')
POD_IP_B=$(kubectl --context "$CTX_B" -n global-vpc-smoke \
  get pod tenant-red-smoke -o jsonpath='{.status.podIP}')

kubectl --context "$CTX_A" -n global-vpc-smoke exec tenant-red-smoke -- \
  wget -T 5 -qO- "http://${POD_IP_B}:8080/"
kubectl --context "$CTX_B" -n global-vpc-smoke exec tenant-red-smoke -- \
  wget -T 5 -qO- "http://${POD_IP_A}:8080/"
```

Both requests must return `tenant-red-smoke`. This proves basic bidirectional
HTTP connectivity, not throughput, failover or full path MTU. Follow with
end-to-end DF probes using a tool that supports them and workload-specific
failure/capacity tests in the target deployment.

Remove the two test Pods when finished; leave the namespace unless it is still
dedicated to this test. The Global VPC stays installed:

```sh
for ctx in "$CTX_A" "$CTX_B"; do
  kubectl --context "$ctx" -n global-vpc-smoke delete pod tenant-red-smoke
done
```

## Other transports

The same CRD, Deployment and `SiteVpc` YAML apply to all three profiles. For a
**fresh** native deployment, replace the ConfigMap's `gateway.json` with the
appropriate registration and adapt both endpoints:

- [Geneve/BGP](../config/samples/site-gateway-geneve-bgp.json)
- [VXLAN/EVPN](../config/samples/site-gateway-vxlan-evpn.json)

Set `site.json.gatewayRevision` to the selected registration's `revision`
(`registration-transports-v3` in those examples). Native profiles require
`trustedUnderlay: true` and no WireGuard Secret. Follow the
[transport guide](transport-profiles.md) for paired VNIs, EVPN health IPs,
RD/RT identity and existing host source addresses. These two JSON examples are
Site A templates; the full paired quick start above is WireGuard.

Do not change an accepted ConfigMap to switch profile, change peers or rotate
keys: immutable plan/runtime hashes reject that migration. Stop new workload
admission, drain existing workloads, delete the SiteVpc and let its finalizer
complete under the original registration before recreating. Keep the controller
running throughout deletion. Private-key Secrets and IPAM reservations are
retained. See [recovery and deletion](site-controller.md#recovery-and-deletion).
